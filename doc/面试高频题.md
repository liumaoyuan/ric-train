### Q2：你这个项目用了哪些 LLM？怎么选的？

**回答要点：**

项目用了两个模型：
- **DeepSeek v4-flash**：Agent 核心推理（call_model 节点），成本约 Qwen 的 1/5，速度快
- **通义千问 Qwen**：知识检索的 Embedding 生成（text-embedding-v3, 768 维）、联网搜索（内置 enable_search 参数）

**选型逻辑：** 不是所有场景都需要最强的模型，核心推理用 DeepSeek 已经足够，Qwen 强在 Embedding 和联网能力。双模型组合既能保证效果又能控制成本。

---

### Q3：为什么选 LangGraph 而不是 LangChain AgentExecutor？

**回答要点：**

AgentExecutor 最大的问题是**执行逻辑黑盒**——你没法精细控制中间步骤，Debug 困难。LangGraph 的 StateGraph 让执行流完全可编程：

```
call_model → 条件判断 → call_tool（可循环）或 summary_node 或 END
```

三个核心优势：
1. **执行流可见**：三个独立节点 + 条件边，每个节点能单独测试、单独加重试策略
2. **原生 Checkpointer**：AsyncRedisSaver 按 thread_id 天然隔离会话，不需要手动管理 Redis 消息列表
3. **NodeInterrupt**：关键操作（比如差评回复）可以插入人工审核节点，AgentExecutor 做不到

但注意 LangGraph 底层仍然依赖 LangChain 的消息体系和工具定义，两者是配合关系不是替代关系。

### Q4：LLM 调用成本怎么控制的？效果如何？

**回答要点：**

三条措施并举：

1. **双模型策略**：DeepSeek 做推理（省 80% 成本）、Qwen 做 Embedding（准确度高）
2. **分层分析**：数据分析不走"把千万级原始数据喂给 LLM"的笨办法，而是 SQL 预聚合 → 只传结构化指标（<500 tokens）→ LLM 解读
3. **语义缓存（规划中）**：相似问题（cosine > 0.95）直接返回 Redis 缓存，预期再省 15%

结果：月 LLM 费用控制在 **1000 元以内**。

## 二、LangGraph / Agent 类问题

### Q7：LangGraph 的 StateGraph 是怎么工作的？画一下你的 Agent 图

**回答要点：**

StateGraph 的核心思想是"有状态的图执行流"。每个节点是一个处理函数，边控制执行方向，状态在节点间传递。

我项目的图结构：

```
用户输入 → call_model（LLM 推理+工具选择）
               │
               ├── 需要工具 → call_tool（执行 @tool 函数）
               │                    │
               │                    └── 回到 call_model（循环）
               │
               ├── 对话过长 → summary_node（AI 摘要压缩）
               │
               └── 完成 → SSE 流式回复用户
```

关键实现细节：
- `AgentState` 是 TypedDict，只包含 `messages: Annotated[Sequence[BaseMessage], add_messages]`
- `add_messages` 是 LangGraph 的 reducer，自动追加新消息到列表
- 条件边 `should_continue()` 判断 LLM 输出是否有 tool_calls
- System Prompt 在 call_model 节点**动态注入**，不持久化到 Checkpointer
- call_model 节点有**孤儿 tool_call 清理逻辑**——中断残留的 tool_calls 自动过滤，防止死循环

---

### Q8：全局单例 Agent 怎么做会话隔离的？多用户同时用会不会串？

**回答要点：**

这是一个经典问题。全局单例只缓存**图结构 + 工具注册**，不保存任何会话状态。

```python
_role_agents: dict[str, CompiledStateGraph] = {}

async def get_agent_for_role(role_codes):
    key = ":".join(sorted(role_codes))
    if key not in _role_agents:
        _role_agents[key] = build_agent(saver)  # 全局共享 AsyncRedisSaver
    return _role_agents[key]

# 使用方：会话隔离靠 thread_id
config = {"configurable": {"thread_id": session_id, "role_codes": roles}}
agent = await get_agent_for_role(roles)
async for event in agent.astream(input, config): ...
```

为什么不会串：编译后的 StateGraph 实例是**纯函数式执行流**，状态全部由 Checkpointer 管理。Checkpointer 按 `thread_id` 区分不同会话的状态快照，天然隔离。你可以理解为：所有人共用同一套"菜谱"，但各自用自己的"灶台"。

---

### Q9：summary_node 是怎么做记忆压缩的？为什么不在 Checkpointer 里全量保存？

**回答要点：**

多轮对话消息累积会导致两个问题：token 成本激增 + 超过模型上下文窗口。

`summary_node` 在两种条件下触发：
- 消息轮次 > 15 轮
- 消息总字符 > 5000

触发后用 LLM 对**早期对话**生成摘要，只保留**最近 5 轮完整消息**，然后用 `RemoveMessage` 删除旧消息。

这是平衡策略：相比固定截断（丢失信息）和全量保留（成本高），AI 摘要 + 保留最近 N 轮是最实用的方案。

摘要会双写到 MySQL（`ai_summary` 字段）和 Redis（TTL 7 天），前端会话列表展示摘要内容。

---

### Q10：Agent 工具执行失败怎么办？降级策略怎么设计的？

**回答要点：**

多级降级：

| 异常 | 处理 | 用户体验 |
|------|------|----------|
| Qwen API 限流/超时 | 指数退避重试（最多 3 次），自动切 DeepSeek | 无感知 |
| 全部模型不可用 | 返回"服务繁忙" | 降级提示 |
| SQL 执行失败 | LLM 根据错误信息自修复，重试 1 次 | 无感知 |
| 图执行崩溃 | Checkpointer 恢复到最后 checkpoint | 需重发 |

NL2SQL 还有一层自我保护：SQL 执行失败后，错误信息 + Schema 重新发给 LLM 修正 SQL，不是直接报错。

---

### Q11：你们的 Agent 和工具是怎么解耦的？新增一个工具要改多少代码？

**回答要点：**

解耦做得比较干净：

1. 每个工具是一个 `@tool` 装饰的 async 函数，定义在 `tools.py`
2. `TOOL_MAP` 字典做工具名到函数的映射
3. `_pick_tools()` 按角色过滤（加盟商不能联网搜索）
4. LLM 通过 tool calling 自动选择工具

新增工具只需要：
1. 在 `tools.py` 加一个 `@tool` 函数
2. 在 `TOOL_MAP` 注册
3. 在 `_pick_tools()` 配置角色可见性

不需要改 graph、不需要改 agentManager、不需要改 chatService。这就是接口隔离的好处。

## 三、RAG / 知识库类问题

### Q12：完整的 RAG 流程是怎么设计的？

**回答要点：**

全链路分两段：

**文档入库（离线）：**
```
上传 → MinIO 存储 → 文本提取（PDF/Word/TXT/MD）
  → 分块（固定长度/段落/递归三种策略）
  → 前端逐块预览确认（人机协同）
  → 异步向量化 → Qwen Embedding → Milvus 存储
  → RAGAS 评估（可选，6 项指标质检）
```

**在线检索：**
```
用户问题 → Embedding 向量化 → Milvus COSINE 搜索
  → 权限过滤（permission_scope 标量 expr）
  → Top-K 召回 → LLM 基于上下文生成回答
  → 无命中时降级为通用知识 + 声明"非企业知识"
```

关键在**人机协同**：分块预览确认后才向量化，避免错误分块污染知识库。

---

### Q13：RAG 质量怎么保证？用了哪些指标？

**回答要点：**

集成 RAGAS 框架做量化评估，6 项指标：

| 指标 | 目标 | 含义 |
|------|------|------|
| Faithfulness | >85% | 生成内容忠实于检索结果，不瞎编 |
| Answer Relevancy | >90% | 回答和问题相关 |
| Context Recall (≈Hit Rate) | >90% | 检索结果包含正确答案 |
| Context Precision (≈MRR) | >0.85 | 正确答案排在前面 |
| Hit Rate（自实现，jieba 分词） | >90% | 基于关键词重叠率的命中检测 |
| MRR（自实现） | >0.85 | 正确答案的排序倒数均值 |

每次知识库更新后可以触发异步评估，作为质量门禁。同时支持按文档评估和全库评估两种粒度。

---

### Q14：Milvus 里怎么做的权限隔离？加盟商不能查到总部文档

**回答要点：**

Milvus Collection 的 schema 里有一个 `permission_scope` 标量字段，取值：
- `all`：全部可见
- `employee_only`：仅老板和员工
- `franchisee_only`：仅老板和加盟商

检索时通过 Milvus 的 `expr` 参数做标量过滤：

```python
expr = "permission_scope in ['all', 'franchisee_only']"  # 加盟商只能看这些
results = collection.search(
    data=[embedding],
    anns_field="embedding",
    param={"metric_type": "COSINE"},
    limit=top_k,
    expr=expr,  # 权限过滤
)
```

这样在向量检索层面就完成了权限隔离，不需要在上层应用层再做过滤，性能更好。

---

### Q15：文档分块策略怎么选的？不同文档用不同策略吗？

**回答要点：**

支持 3 种分块策略，上传文档时可选：

| 策略 | 实现 | 适用场景 |
|------|------|----------|
| 固定长度 | 按 max_tokens=500 + overlap=50 切 | 通用文档，默认 |
| 段落分割 | 按自然段落（\n\n）切 | 制度文档，段落完整 |
| 递归分块 | 段落→句子递归切 | 长文档，精细控制 |

中文 token 估算规则：`中文字符数/1.5 + 英文单词数 + 其他字符*0.25`，不是精确 tokenizer 但够用。

## 四、NL2SQL / 数据类问题

### Q16：NL2SQL 怎么保证安全性？LLM 生成的 SQL 乱来怎么办？

**回答要点：**

三层安全防护：

1. **SELECT-only 硬校验**：检查 SQL.strip().upper() 是否以 SELECT 开头，不是就直接拒绝
2. **危险关键词黑名单**：DROP/DELETE/UPDATE/INSERT/ALTER/CREATE/TRUNCATE/EXEC 正则匹配，命中即拒绝
3. **门店 scope 隔离**：加盟商的查询自动拼接 `store_ids` 白名单，只能查自己的店

此外还有两道软防护：
- 自动加 `LIMIT 200` 防止结果过大
- SQL 执行失败时 LLM 根据错误信息自修复，最多重试 1 次

**面试官追问："SELECT 里可以嵌子查询做 DELETE 吗？"** → 子查询也受黑名单控制，而且数据库连接用的只读事务，INSERT/UPDATE/DELETE 在数据库层面就被拒绝了。双层保险。

---

### Q17：NL2SQL 的完整执行链路是什么样的？

**回答要点：**

```
用户自然语言问题
  → Schema 注入（7 张业务表的 DDL + 字段中文说明 + 示例数据）
  → LLM 生成 SQL（默认加"查上月"避免全量扫描）
  → SQL 清洗（去掉 markdown 代码块 ```sql 标记）
  → 安全校验（SELECT-only + 黑名单）
  → 执行查询（ConnectionManager + asyncio.to_thread 避免阻塞）
  → SQL 失败？→ LLM 根据 Schema + 错误信息修正 → 重试
  → LLM 总结结果（自然语言回答用户）
```

Schema 注入是关键——DDL 带了字段中文注释和示例值，LLM 才能准确理解"客单价"对应哪个字段。

---

### Q18：海量数据怎么分析？千万级订单不可能全喂给 LLM

**回答要点：**

分层分析策略：

```
原始数据（千万级） → SQL 预聚合 → 指标体系（<500 tokens）→ LLM 分析
```

具体三步：
1. **SQL 预聚合**：从 `daily_summary` 表（每店每日一条汇总），不接触原始订单明细
2. **指标计算**：Python 层完成同比环比计算，只传入结构化数值（营收、客单价、翻台率等）
3. **LLM 分析**：基于指标生成"数据概览 → 关键发现 → 改进建议"三段式报告

发现异常时可以**分层下钻**：按需查日维度明细确认。预聚合结果缓存到 Redis（TTL=1 小时）。

### Q19：RBAC 权限模型在项目中怎么落地的？

**回答要点：**

标准 RBAC 三张核心表：

前端路由也动态渲染：根据后端返回的菜单树控制页面可见性。

### Q20：SSE 流式响应是怎么实现的？和 WebSocket 比为什么选 SSE？

**回答要点：**

**选 SSE 不选 WebSocket 的原因：** 我们的场景是单向数据流（服务端 → 客户端推送 token），不需要客户端 → 服务端的实时通信。SSE 基于 HTTP 协议，浏览器原生支持，不需要额外库，实现成本低。

**实现方式：**

```python
# 后端（FastAPI）
@app.post("/api/v1/chat/ask")
async def ask(request: AskParam):
    async def event_generator():
        async for token in chat_service.ask_stream(question, session_id):
            yield f"data: {json.dumps({'type': 'content', 'content': token})}\n\n"
        yield f"data: {json.dumps({'type': 'done'})}\n\n"
    return StreamingResponse(event_generator(), media_type="text/event-stream")

# 前端（fetch + ReadableStream）
const reader = response.body.getReader();
while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    // 逐 chunk 解析 SSE 事件，更新 UI
}
```

前端支持 `AbortController` 取消请求。流式输出只过滤 `call_model` 节点的 token，工具调用产生的中间信息不推送给用户。

### Q21：LangFuse 在项目中怎么用的？追踪哪些数据？

**回答要点：**

LangFuse 通过 `@observe` 装饰器集成，覆盖 Agent 的全链路：

```python
@observe()
async def call_model(state: AgentState, config: RunnableConfig):
    # LangFuse 自动追踪：LLM 调用、token 消耗、耗时
    ...

@observe()
async def call_tool(state: AgentState, config: RunnableConfig):
    # LangFuse 自动追踪：工具选择、工具执行结果
    ...
```

追踪的数据维度：

| 维度 | 用途 |
|------|------|
| 调用轨迹（完整 ReAct 推理链） | Debug 和问题排查 |
| Token 消耗 + 模型 + 费用 | 成本核算 |
| 各工具调用频次/成功率 | 使用洞察 |
| 用户反馈（点赞/点踩） | 质量评估 |

每月产出 LLM 调用分析报告，驱动持续优化。

### Q22：AsyncRedisSaver Checkpointer 的工作原理是什么？

**回答要点：**

Checkpointer 是 LangGraph 内置的持久化层，每次图执行结束后**自动调用** `checkpoint.put()` 保存当前状态快照到 Redis。下次同一 `thread_id` 恢复时，`checkpoint.get()` 自动加载历史消息。

关键配置：
- TTL = 3 天（会话不会无限期保留）
- `refresh_on_read = True`（每次读取刷新 TTL，活跃会话持续有效）
- Redis key 格式：`checkpoint:{thread_id}:{checkpoint_id}`

好处：完全不需要手动管理消息列表，不需要 `push_to_redis()` / `load_from_redis()`，Checkpointer 在 StateGraph 内部全部自动完成。

## 六、LLM / AI 基础类问题

### Q23：讲一下 RAG 和微调的区别，什么时候用 RAG 什么时候用微调？

**回答要点：**

| 维度 | RAG | 微调 |
|------|-----|------|
| 知识更新 | 替换文档即可，分钟级 | 重新训练，小时~天级 |
| 幻觉控制 | 有检索上下文，可控 | 靠模型记忆，不可控 |
| 长尾知识 | 只要文档库里有的都能回答 | 需要足够训练样本 |
| 成本 | 每次推理↑（检索+长上下文） | 训练成本高，推理成本低 |
| 适用场景 | 企业知识库、制度问答、实时信息 | 风格适配、格式控制、特定任务 |

**这个项目为什么选 RAG 不选微调：** 连锁餐饮的制度、菜品知识频繁更新（新品上市、促销政策调整），RAG 只需要更新文档就能立即生效，微调跟不上这个节奏。而且加盟商问的问题很多是长尾的（"某道菜的做法"），RAG 天然适合。

---

### Q24：Embedding 模型怎么选的？向量维度多少？

**回答要点：**

我们用的是 Qwen 的 `text-embedding-v3` 模型，768 维。

选型考虑：
1. 和 Qwen LLM 同一生态，兼容性好
2. 768 维是效果和性能的平衡点——太低语义表达不够，太高检索性能下降
3. 通义千问的 Embedding 对中文支持好

相似度计算用 **COSINE 距离**，Milvus 原生支持。

### Q25：什么是 Prompt Engineering？你们项目里怎么做的？

**回答要点：**

Prompt Engineering 在项目里体现在几个地方：

1. **System Prompt 版本管理**：从代码抽离到 MySQL/配置中心，支持热更新，不用重启服务
2. **Schema 注入**：NL2SQL 的 System Prompt 包含 7 张表的 DDL + 字段中文说明 + 示例值
3. **工具描述**：`@tool` 的 docstring 就是 LLM 理解工具用途的 Prompt，描述精确度直接影响工具选择的准确率
4. **记忆压缩 Prompt**：summary_node 的摘要生成指令

System Prompt 设计时注意了**不在 Checkpointer 里持久化**，每次在 call_model 节点动态注入，否则恢复会话时会累积冗余的 SystemMessage。

## 七、场景设计题

### Q26：如果一个加盟商问"帮我查一下上个月的营收"，背后发生了什么？

**回答要点：**

完整链路：

1. 前端 POST `/api/v1/chat/ask` 发送问题 + session_id
2. `chatService.ask_stream()` 恢复会话（Checkpointer 加载历史）
3. Agent 的 `call_model` 节点调用 LLM 选择工具
4. LLM 判断这是数据类问题 → 调用 `data_query` 工具
5. `data_query` 注入 Schema → LLM 生成 SQL（加 WHERE store_id 和 上月时间范围）
6. SQL 安全校验 → 执行查询
7. LLM 将查询结果总结为自然语言
8. `call_model` 节点逐 token SSE 推送给前端
9. Checkpointer 自动保存状态 → MySQL 持久化对话记录

整个过程通常在 **5 秒内**完成。

### Q27：如果 Qwen API 挂了，系统怎么应对？

**回答要点：**

多级降级：
1. **重试 + 降级模型**：call_model 节点捕获异常 → 指数退避重试 → 切换到 DeepSeek 继续执行
2. **功能降级**：Qwen 独有的能力（联网搜索、Embedding）暂时不可用，但核心对话能力不受影响
3. **最终兜底**：如果 DeepSeek 也挂了，返回"服务繁忙，请稍后再试"

另外会影响到的功能：
- 知识库检索：Qwen Embedding 不可用，降级为关键词 BM25 检索（稀疏向量已在 Milvus 中建立）
- 联网搜索：不可用时 data_query 无法获取实时信息
- 对话记忆压缩：summary_node 暂时不触发，直到模型恢复

总原则：**尽力降级，不全部瘫痪**。

---

### Q28：500 家门店，如果每个加盟商同时发消息，怎么保证并发？

**回答要点：**

三层支撑：

1. **API 层**：FastAPI 异步框架，单进程就能处理上千并发连接，瓶颈不在 API
2. **Agent 层**：全局单例 + thread_id 会话隔离，StateGraph 是纯函数式执行，同一个实例可以同时处理多个请求
3. **LLM 层**：这是真正的瓶颈。通过语义缓存（重复问题直接返回）+ 双模型分流（DeepSeek 便宜可以多调用）缓解

实际估算：加盟商不是高频用户（一天问几次），500 家门店的同时在线可能不到 50 个，当前的架构完全可以支撑。

监控方面 LangFuse 追踪每次调用的耗时和 Token 消耗，方便提前发现性能瓶颈。

### Q29：如果让你设计一个"AI 差评回复建议"功能，你怎么做？

**实际项目中该功能在 Phase 2 规划中。回答要点：**

```
差评 → AI 分析（情感分析+问题标签提取）
  → LLM 生成回复建议（安抚语气 + 解释原因 + 改进承诺）
  → NodeInterrupt 中断 → 店长审核确认
  → 店长一键发布
```

技术要点：
1. **AI 分析**：提取差评中的关键问题（口味、服务、环境等），自动打标签
2. **生成策略**：结合门店信息、菜品信息做个性化回复，不套模板
3. **人机协同**：用 LangGraph 的 NodeInterrupt 机制，在 call_tool 执行完后插入人工审核节点
4. **审核界面**：展示 AI 建议 + 一键采纳/编辑/忽略

### Q30：你们的项目架构有什么不足之处？如果重来你会怎么改进？

**回答要点：**（这个问题考察反思能力，说一两个真实痛点就好）

两个可以做得更好的地方：

1. **评估体系**：当前 RAGAS 评估需要人工准备测试用例，覆盖不全。应该建立 CI 自动化的回归测试集，每次知识库变更自动跑全量评估
2. **可观测性深度**：LangFuse 已经接入，但缺少告警机制——当 LLM 调用失败率突增或 Token 消耗异常时应该自动告警

另外 NL2SQL 的 Precision/Recall 还没有正式评估，现在只是功能上能用，缺少量化指标来衡量 SQL 生成的准确率。
