# 连锁餐饮 AI 系统 — 面试准备

> 本文档用于 AI 应用开发工程师面试准备，基于代码实际实现状态撰写，区分已实现与规划中功能。

---

## 1. 项目概述

### 1.1 一句话介绍

基于 LangGraph StateGraph + FastAPI 构建的连锁餐饮 AI 辅助管理系统，面向 500 家门店的加盟体系，提供 AI 智能问答（RAG 检索 + NL2SQL 真实执行）、知识库管理、风评监控等能力。

### 1.2 核心数据

| 维度 | 数值 |
|------|------|
| 覆盖门店 | 500 家（全国 31 省） |
| 用户角色 | 3 种（老板/员工/加盟商） |
| 技术栈 | Python / FastAPI / LangGraph / Vue 3 |
| 数据量级 | 订单千万级，评论数万级 |
| LLM 月费用目标 | < 1000 元 |
| Agent 框架 | LangGraph 1.0 + AsyncRedisSaver Checkpointer |

## 2. 技术架构与选型

### 2.1 整体架构

```
Vue 3 (前端)
  ↓ HTTP/SSE
FastAPI (API 层)
  ↓
Service Layer (业务服务)
  ├── LangGraph StateGraph Agent (聊天助手)
  │     ├── knowledge_search (Milvus RAG 检索)
  │     ├── data_query (真实 NL2SQL 执行)
  │     ├── web_search (联网搜索)
  │     └── general_chat (闲聊兜底)
  ├── Knowledge Service (知识库管理)
  ├── RBAC Auth (权限)
  └── Data API (数据查询)
  ↓
Infrastructure
  MySQL / Redis / Milvus / MinIO
```

### 2.2 技术选型

| 技术 | 选型理由 |
|------|---------|
| **FastAPI** | 异步高性能，原生支持 SSE 流式，Pydantic 校验，适配 LLM 流式场景 |
| **LangGraph** | StateGraph 提供有状态图执行流，Checkpointer 按 thread_id 天然隔离会话，RedisSaver 持久化状态快照 |
| **AsyncRedisSaver** | LangGraph 内置的异步 Redis Checkpointer，3 天 TTL + refresh_on_read，替代手动管理消息列表 |
| **Milvus** | 768 维 Embedding 向量检索，支持 expr 标量过滤实现权限隔离，混合检索 |
| **MinIO** | 知识库文档存储（PDF/Word/TXT），与 Milvus 配合实现 RAG 全链路 |

### 2.3 为什么不是其他方案

| 方案 | 缺点 |
|------|------|
| **Chain（链式）** | 调用链固定，无法动态决定是否调用工具，不适合多步推理 |
| **LangChain AgentExecutor** | 执行逻辑黑盒，无法精细控制中间步骤，没有原生 Checkpointer |
| **LangGraph 多 Agent** | 当前场景单用户问答+4 个工具一个 Agent 足够，多 Agent 增加协调复杂度，ROI 低 |

## 3. 核心技术点详解（已实现）

### 3.1 LangGraph StateGraph

```
用户输入 → call_model (LLM 判断：注入 System Prompt + 绑定工具)
  ├─ 需要工具 → call_tool (路由到 TOOL_MAP 执行)
  │               └─ 循环回到 call_model
  ├─ 超阈值 → summary_node (AI 摘要压缩 → MySQL + Redis 持久化)
  └─ 完成 → SSE 流式回复
```

**关键代码片段：**

```python
# graph.py — StateGraph 定义
workflow = StateGraph(AgentState)
workflow.add_node("call_model", call_model)
workflow.add_node("call_tool", call_tool)
workflow.add_node("summary_node", summary_node)
workflow.set_entry_point("call_model")
workflow.add_conditional_edges("call_model", should_continue,
    {"call_tool": "call_tool", "summary_node": "summary_node", "__end__": END})
workflow.add_edge("call_tool", "call_model")
return workflow.compile(checkpointer=saver)  # AsyncRedisSaver

# 流式执行（chatService.py）
agent = await get_agent_for_role(role_codes=roles)
async for event in agent.astream({"messages": [msg]}, config, stream_mode="messages"):
    if isinstance(chunk, AIMessageChunk) and node == "call_model":
        yield SSE(chunk.content)
```

**亮点：**
- **Call_model 节点清理孤儿 tool_call**：因中断残留的 AIMessage.tool_calls 与 ToolMessage 不匹配时自动过滤，防止死循环
- **Role-based tool 注入**：`_pick_tools()` 根据角色编码过滤工具，加盟商无 web_search 权限
- **Global singleton agent**：按角色组合缓存 CompiledStateGraph，`agentManager.py` 管理生命周期

### 3.2 RAG 知识库检索

**完整链路（已实现）：**

```
文档上传 → MinIO 存储 (knowledge-docs 桶)
  → 文本提取 (PDF/python-docx/TXT)
  → 分块 (3 种策略：fixed/paragraph/recursive)
  → 前端逐块预览勾选（人机协同）
  → 异步向量化 → Qwen Embedding (text-embedding-v3, 768维)
  → Milvus 存储 (knowledge_chunks 集合)
  → RAGAS 质量评估（6 项指标）
```

**检索链路：**

```
用户问题 → Embedding 向量化 → Milvus COSINE 检索
  → 权限过滤 (permission_scope 标量 expr)
  → Top-K 召回 → LLM 基于上下文生成回答
  → 无命中时降级为通用知识 + 声明非企业知识
```

**档案管理 API（全部已实现）：**

| 接口 | 功能 |
|------|------|
| `POST /upload` | 上传文档，支持 4 种分类 + 3 种分块策略 |
| `POST /{id}/preview` | 分块预览（确认后才向量化） |
| `POST /{id}/vectorize` | 异步向量化（返回 task_id） |
| `POST /{id}/evaluate` | RAGAS 异步评估（上传测试用例 JSON） |
| `GET /task/{task_id}` | 任务进度查询 |
| `POST /search` | 公开 RAG 检索接口 |
| `DELETE /{id}` | 级联删除（DB + Milvus + MinIO） |

**RAGAS 指标（`ragas_eval.py`）：**

| 指标 | 目标 | 说明 |
|------|------|------|
| Faithfulness | > 85% | 生成内容忠实于检索结果 |
| Answer Relevancy | > 90% | 回答与问题的相关性 |
| Context Recall（≈Hit Rate） | > 90% | 检索结果包含正确答案的比例 |
| Context Precision（≈MRR） | > 0.85 | 正确答案在检索结果中的排序 |
| Hit Rate | > 90% | 自定义 jieba 关键词匹配 |
| MRR | > 0.85 | 自定义关键词排序 |

**人机协同：** 分块预览确认后才向量化，避免错误分块污染知识库。

### 3.3 NL2SQL 真实执行

**完整链路（`tools.py` data_query）：**

```
用户问题 → Schema 注入（7 张业务表完整 DDL + 字段说明）
  → LLM 生成 SQL（默认查上月，避免查全量）
  → SQL 清洗（去除 markdown 代码块标记）
  → 安全校验（SELECT-only 检查 + 危险关键词过滤）
  → 执行查询（ConnectionManager + asyncio.to_thread 避免阻塞）
  → 错误重试（SQL 执行失败 → 发给 LLM 修正 → 重新执行）
  → LLM 总结（自然语言回答）
```

**三层安全防护：**

1. **SELECT-only 校验**：`sql.upper().startswith("SELECT")` 硬校验
2. **危险关键词过滤**：DROP/DELETE/UPDATE/INSERT/ALTER/CREATE/TRUNCATE/EXEC 黑名单
3. **Scope 隔离**：加盟商查询自动拼接 `store_ids` 白名单

**异常自愈：** SQL 执行失败时，LLM 根据 Schema + 错误信息自动修正 SQL，最多重试 1 次。

### 3.4 流式响应（SSE）

**后端（`chatService.py`）：**

```python
# 逐 token SSE 推送
async for event in agent.astream(
    {"messages": [input_message]},
    config=config,
    stream_mode="messages",
):
    if isinstance(chunk, AIMessageChunk) and node == "call_model":
        yield SSE({"type": "content", "content": chunk.content})
```

**前端：** `fetch` + `ReadableStream.getReader()` + `AbortController` 取消请求。

### 3.5 全局单例 Agent + Checkpointer 会话隔离

**核心设计：**

```python
# agentManager.py — 全局单例（按角色）
_role_agents: dict[str, CompiledStateGraph] = {}

async def get_agent_for_role(role_codes):
    key = ":".join(sorted(role_codes))
    if key not in _role_agents:
        _role_agents[key] = build_agent(_saver)
    return _role_agents[key]

# 会话隔离通过 thread_id
config = {"configurable": {"thread_id": session_id, "role_codes": roles}}
agent = await get_agent_for_role(roles)
await agent.astream(input, config)
```

**Checkpointer（AsyncRedisSaver）：**
- 全局共享一个 AsyncRedisSaver 实例（3 天 TTL + refresh_on_read）
- `thread_id` = `session_id`，不同会话状态在 Redis 中天然隔离
- 无需手动 push_to_redis / load_from_redis，Checkpointer 自动完成

### 3.6 对话记忆管理

| 层级 | 存储 | 用途 |
|------|------|------|
| Checkpoint | Redis（`checkpoint:{thread_id}`） | LangGraph 自动管理的运行时状态快照（TTL=3天） |
| 摘要 | MySQL（`base_llm_session.ai_summary`）+ Redis（7天） | AI 压缩的会话摘要，供前端展示 |
| 持久化 | MySQL（`base_llm_conversation`）+ Milvus | 全量对话记录，前端历史回顾 |
| 向量 | Milvus | 对话检索 |

**记忆压缩（`summary_node`）：** 超过 15 轮或 5000 字符时，LLM 生成早期对话摘要，保留最近 5 轮完整消息。摘要双写 MySQL + Redis。

### 3.7 Agent 可观测性

- 已集成 **LangFuse tracing**（`@observe` 装饰器覆盖 call_model / call_tool / summary_node）
- 调用轨迹、Token 消耗、响应耗时全链路追踪

## 4. 技术挑战与解决方案

> 面试重点：讲清楚**遇到了什么困难、怎么解决的、为什么这么解决**。

### 挑战 1：全局单例 Agent 与会话隔离

**问题：** 按角色缓存全局单例 Agent 避免重复构建，但多用户共享同一实例导致状态互相干扰。

**方案：** LangGraph `thread_id` 实现会话隔离。编译后的 StateGraph 实例是线程安全的纯函数式执行流，状态全部由 Checkpointer 管理（按 `thread_id` 区分），天然隔离。`agentManager.py` 中的全局单例只缓存图结构 + 工具注册，不保存任何会话状态。

```python
agent = await get_agent_for_role(["admin"])  # 全局单例
config = {"configurable": {"thread_id": session_id}}  # 隔离在此
async for event in agent.astream(input, config): ...
```

### 挑战 2：NL2SQL 安全性与可靠性

**问题：** LLM 生成的 SQL 可能包含危险操作或语法错误。

**方案：** SELECT-only 校验 + 危险关键词黑名单 + 门店 scope 隔离三管齐下。执行失败时 LLM 自修复 SQL，避免一次报错就返回"查不到"。

### 挑战 3：RAG 质量闭环

**问题：** 知识库向量化后无法判断检索质量，知识库更新可能导致质量回退。

**方案：** RAGAS 评估框架集成，6 项指标量化评估。评估异步执行，支持按文档评估和全库评估。人机协同分块确认，避免错误分块污染知识库。

### 挑战 4：LLM 不稳定

**问题：** Qwen API 限流、超时。

**方案：** 双模型策略（Qwen + DeepSeek），知识检索和数据查询用 Qwen（联网能力），Agent 核心推理用 DeepSeek（成本更低、v4-flash 速度快）。全局异常捕获 + SSE error 事件通知前端。

### 挑战 5：长期对话 Token 累积

**问题：** 多轮对话消息累积，15 轮后 token 成本激增。

**方案：** summary_node 条件压缩。超过 15 轮/5000 字符时触发 LLM 摘要，保留最近 5 轮，摘要持久化 MySQL + Redis。相比固定截断（丢失信息）和全量保留（成本高），这是平衡点。

### 挑战 6：文档上传到向量化的全异步流程

**问题：** RAG 流程涉及文件上传、文本解析、分块、向量化、Milvus 写入，每一步都可能耗时数秒到数分钟。

**方案：** 分块预览（同步）→ 确认 → 异步向量化（后台线程 + TaskProgress 进度追踪）。用户上传后实时预览分块，确认后提交向量化任务，前端轮询进度。避免大文件阻塞 API 线程。

## 7. 面试高频问题与回答

### Q1：为什么用 LangGraph 而不用 LangChain AgentExecutor？

> AgentExecutor 的执行逻辑是黑盒，无法精细控制中间步骤。LangGraph 的 StateGraph 让执行流完全可编程：三个独立节点（call_model → call_tool → summary_node），条件边控制路由，Checkpointer 自动持久化。要 Debug 一个 AgentExecutor 的异常行为很难，但在 StateGraph 中可以单独测试每个节点。另外 AsyncRedisSaver 按 thread_id 天然隔离会话，不需要手动管理 Redis 消息列表。但 LangGraph 底层仍然依赖 LangChain 的消息体系和工具定义，两者是配合关系。

### Q2：RAG 项目如何保证质量？

> 核心是建立质量评估闭环。我们集成了 RAGAS 框架用 6 项指标（Faithfulness、Answer Relevancy、Context Recall、Context Precision、Hit Rate、MRR）量化评估。每次知识库更新后可以异步运行评估，不达标阻断上线。另外设计了人机协同机制——文档分块后前端逐块预览确认，避免错误分块污染知识库。这个"质量门禁"意识在企业级落地中至关重要。

### Q3：NL2SQL 怎么做安全防护？

> 三层：第一层 SELECT-only 硬校验，非 SELECT 查询直接拒绝；第二层危险关键词黑名单（DROP/DELETE/UPDATE/INSERT/ALTER/CREATE等）；第三层门店 scope 注入，加盟商的查询自动限定 `store_ids` 白名单。此外，SQL 执行失败会发给 LLM 根据错误信息自修复，避免一次报错就返回"查不到"。

### Q4：怎么控制 LLM 调用成本？

> 两点：1) 双模型策略，Agent 核心推理用 DeepSeek v4-flash（成本约为 Qwen 的 1/5），知识检索和数据查询用 Qwen（准确度更高）；2) 分层分析，NL2SQL 查到的数据直接由 LLM 总结，不把原始数据全量塞给 LLM。语义缓存规划在 Phase 2 落地，预期再节省 15%。

### Q5：你这个项目有什么实际业务价值？

> 三个维度：降本（总部数据分析效率提升，重复咨询被 AI 消化）、提效（加盟商问题响应从 4 小时缩短到即时）、增收（及时的差评回复挽回客户流失）。每个指标都有明确的测量方法和 baseline，详见需求文档。

### Q6：听说你用的 StateGraph，有没有遇到什么坑？

> 有两个典型问题：第一，孤儿 tool_call 问题——网络中断或异常退出导致 AI 消息有 tool_calls 但缺少对应 ToolMessage，会让 Agent 陷入死循环。我们在 call_model 节点加了清理逻辑，自动过滤匹配不上的 tool_call。第二，System Prompt 不应该放到 Checkpointer 里持久化，否则每次恢复会话都会累积冗余的 SystemMessage。我们的做法是在 call_model 节点动态注入，不写入 state.messages 的持久化流。
