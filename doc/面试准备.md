# 连锁餐饮 AI 系统 — 面试准备

> 本文档用于 AI 应用开发工程师面试准备，涵盖项目概述、技术选型、核心实现、挑战与解决方案、高频面试题。

## 1. 项目概述

### 1.1 一句话介绍

基于 LangGraph + FastAPI 构建的连锁餐饮 AI 辅助管理系统，面向 500 家门店的加盟体系，提供 AI 数据分析、智能问答、风评监控、知识库 RAG 等能力。

### 1.2 核心数据

| 维度 | 数值 |
|------|------|
| 覆盖门店 | 500 家（全国 31 省） |
| 用户角色 | 3 种（老板/员工/加盟商） |
| 技术栈 | Python / FastAPI / LangGraph / Vue 3 |
| 数据量级 | 订单千万级，评论数万级 |
| LLM 月费用目标 | < 1000 元 |

## 2. 技术架构与选型

### 2.1 整体架构

```
Vue 3 (前端)
  ↓ HTTP/SSE
FastAPI (API 层)
  ↓
Service Layer (业务服务)
  ├── LangGraph Agent (聊天助手)
  ├── NL2SQL Service (数据分析)
  ├── RAG Pipeline (知识库检索)
  ├── Review Analysis (风评)
  └── RBAC Auth (权限)
  ↓
Infrastructure
  MySQL / Redis / Milvus / MinIO
```

### 2.2 技术选型

| 技术 | 选型理由 |
|------|---------|
| **FastAPI** | 异步高性能，原生支持 SSE 流式，类型校验通过 Pydantic，天然适配 LLM 流式场景 |
| **LangGraph** | 相比 LangChain AgentExecutor 提供更细粒度的执行流控制（有状态图），原生 Checkpointer 持久化，节点级 RetryPolicy，NodeInterrupt 机制 |
| **Redis** | 项目已有基础设施，承担语义缓存、短期 checkpoint、会话 Token 等多重角色，无需引入新中间件 |
| **Milvus** | 专门针对 768 维 Embedding 向量检索优化，支持混合检索（向量+标量过滤），权限隔离通过 expr 实现 |

### 2.3 为什么不是其他方案

| 方案 | 缺点 |
|------|------|
| **Chain（链式）** | 调用链固定，无法动态决定是否调用工具，不适合需要多步推理的场景 |
| **LangChain AgentExecutor** | 执行逻辑黑盒，无法精细控制中间步骤，没有原生 Checkpoint 和 Interrupt |
| **LangGraph 多 Agent** | 当前场景（单用户问答+工具调用）一个 Agent 足够，多 Agent 增加协调复杂度，ROI 低 |

面试回答方向：不是越复杂的架构越好，而是**最匹配当前业务复杂度的架构才是好架构**。

## 3. 核心技术点详解

### 3.1 LangGraph StateGraph

```
用户输入 → call_model (LLM 判断)
  ├─ 需要工具 → call_tool (路由到 @tool)
  │               └─ 循环回到 call_model
  ├─ 超阈值 → summary_node (AI 摘要压缩)
  └─ 完成 → 回复用户
```

**为什么用 StateGraph？**

- **有状态图**：天然支持多轮对话的状态管理，每次执行自动走完图的完整流
- **Checkpointer**：LangGraph 内置的持久化层，按 `thread_id` 保存状态快照，不需要手动管理 Redis 消息列表
- **节点级重试**：`RetryPolicy` 直接在编译时声明，比手写 try-except 更可靠
- **NodeInterrupt**：在关键节点（如差评回复审核）插入中断，等待用户确认后恢复执行

**关键代码片段：**

```python
# StateGraph 定义
graph = StateGraph(AgentState)
graph.add_node("call_model", call_model_node,
    retry=RetryPolicy(max_attempts=3, backoff_factor=2.0,
                      fallback_model=deepseek_llm))
graph.add_node("call_tool", tool_executor_node)
graph.add_node("summary_node", summary_compress_node)
graph.add_conditional_edges("call_model", should_continue, {...})
graph.set_entry_point("call_model")
app = graph.compile(checkpointer=MemorySaver())

# 流式执行
async for event in app.astream(input, config, stream_mode="messages"):
    yield event
```

### 3.2 RAG 知识库检索

**完整链路：**

```
文档上传 → MinIO 存储 → 文本提取 (PDF/Word)
  → 分块 (4种策略可选)
  → 前端逐块预览勾选（人机协同）
  → 确认 → Embedding 向量化 → Milvus 存储
  → RAGAS 质量评估（CI 门禁）
```

**检索链路：**

```
用户问题 → Embedding 向量化 → Milvus 混合检索
  → 权限过滤 (scalar expr) → ReRank 重排序
  → LLM 生成回答 + 引用溯源
```

**RAGAS 指标：**

| 指标 | 目标 | 说明 |
|------|------|------|
| Hit Rate | > 90% | 检索结果包含正确答案的比例 |
| MRR | > 0.85 | 正确答案在检索结果中的平均排序 |
| Faithfulness | > 85% | 生成内容忠实于检索结果的比例 |
| Answer Relevancy | > 90% | 回答与问题的相关性 |

面试回答方向：RAG 不只是"向量检索+LLM"，**质量评估闭环**才是企业级落地的关键。Hit Rate 高不代表回答好，还需要 Faithfulness 保证不杜撰。

### 3.3 NL2SQL 真实执行

```
用户问题 → Schema 注入（表结构+字段说明）
  → LLM 生成 SQL
  → 语法校验 + 安全过滤（只读 + 白名单 + LIMIT）
  → 执行查询
  → 结果格式化 + LLM 总结
```

**三层安全防护：**

1. **数据库连接层面**：只读事务，从根本上禁止写操作
2. **SQL 语法层面**：表名白名单校验，自动加 LIMIT 200
3. **异常处理层面**：SQL 执行错误发给 LLM 自修复，最多重试 2 次

### 3.4 语义缓存

```
问题 → md5(question) + role → Redis 查询
  → 命中 → 直接返回（零成本）
  → 未命中 → Agent 执行 → 存入 Redis
```

- 键格式：`semantic_cache:{role}:{md5(question)}`
- 语义相似度：Embedding cosine > 0.95 命中（但向量不存 Milvus，直接在 Redis 处理）
- TTL 按场景区分：闲聊 1h / 知识 24h / 数据 10min / 搜索不缓存
- 预期命中率 ~20%，月均节省 LLM 费用 ~15%

### 3.5 流式响应（SSE）

**后端：**

```python
async def ask_stream(question, session_id):
    config = {"configurable": {"thread_id": session_id}}
    async for event in agent.astream({"messages": [msg]}, config):
        if "content" in event:
            yield f"data: {json.dumps({'type': 'content', 'content': event['content']})}\n\n"
    yield "data: {\"type\": \"done\"}\n\n"

return StreamingResponse(ask_stream(...), media_type="text/event-stream")
```

**前端：**


## 4. 技术挑战与解决方案

> 面试重点：不要只说"做了什么"，要讲清楚**遇到了什么困难、怎么解决的、为什么这么解决**。

### 挑战 1：全局单例 Agent 与会话隔离的矛盾

**问题：** 按角色缓存全局单例 Agent 可以避免重复构建，但多用户共享同一个 Agent 实例会导致会话状态互相干扰。LangChain 的 `create_agent()` 没有内置的会话隔离机制。

**方案：** 利用 LangGraph 的 `thread_id` 实现会话隔离。Checkpointer 按 `thread_id` 区分状态快照，不同会话的状态在 Checkpointer 层天然隔离。全局单例只负责图结构和工具注册，不保存任何会话状态。

```python
# 全局单例（按角色）
_role_agents: dict = {}

async def get_agent_for_role(role_codes):
    key = ":".join(sorted(role_codes))
    if key not in _role_agents:
        _role_agents[key] = build_graph(role_codes)
    return _role_agents[key]

# 会话隔离通过 thread_id
config = {"configurable": {"thread_id": session_id}}
await agent.astream(input, config)
```

**对比：** 旧方案用 `contextvars` 手动管理上下文，容易遗漏清理；Checkpointer 方案无需手动管理，且自动持久化。

### 挑战 2：NL2SQL 安全性

**问题：** LLM 生成的 SQL 不可控，"帮我查一下数据"可能变成 `DROP TABLE orders;`。或者生成效率极低的查询导致数据库 OOM。

**方案：** 三层防护 + 异常自愈。

```python
def validate_and_execute(sql: str) -> list:
    # 第一层：语法解析，禁止非 SELECT 语句
    if not sql.strip().upper().startswith("SELECT"):
        raise SecurityError("只允许查询操作")

    # 第二层：表名白名单
    allowed_tables = {"daily_summary", "store", "dish", "order_item", "review"}
    parsed_tables = extract_tables(sql)
    if not parsed_tables.issubset(allowed_tables):
        raise SecurityError(f"不允许访问表: {parsed_tables - allowed_tables}")

    # 第三层：自动加 LIMIT
    sql = ensure_limit(sql, max_rows=200)

    # 只读事务执行
    with db.transaction(read_only=True):
        return db.execute(sql)
```

### 挑战 3：LLM 调用不稳定

**问题：** Qwen API 频繁限流、偶尔超时，用户体验差（"AI 没反应"）。

**方案：** 多级降级 + LangGraph RetryPolicy。

```
Qwen API 限流/超时
  → 指数退避重试（1s → 2s → 4s，最多 3 次）
  → 自动切换 DeepSeek 模型重试
  → 全部不可用 → 返回"服务繁忙，请稍后再试"
  → 图执行崩溃 → Checkpointer 恢复到上次 Checkpoint
```

### 挑战 4：海量数据无法直接送入 LLM

**问题：** 千万级订单数据，无法直接作为 LLM 上下文。且 LLM 不擅长精确计算，直接"计算上月总营收"会出错。

**方案：** 分层分析策略。

```
原始数据 (千万级)
  → SQL 预聚合 (daily_summary 表，每店每日一条)
  → Python 指标计算 (同比环比，< 500 tokens)
  → LLM 分析 (异常解读、亮点提取、改进建议)
```

LLM 只负责"解读"而非"计算"，精准计算交给 SQL，LLM 做它擅长的事。

### 挑战 5：记忆管理与 Token 成本

**问题：** 多轮对话中消息不断累积，15 轮后 token 消耗激增，LLM 调用成本上升且容易超出上下文窗口。

**方案：** LangGraph Checkpointer + summary_node 压缩。

- Checkpointer 自动持久化全量对话，不丢失历史
- 超 15 轮或 5000 字符时触发 summary_node，用 LLM 对早期对话做智能摘要
- 保留最近 5 轮完整对话，历史转为摘要
- 相比固定截断（丢失信息）和全量保留（成本高），这是成本与体验的平衡点

## 6. 面试高频问题与回答

### Q1：为什么用 LangGraph 不用 LangChain AgentExecutor？

> LangGraph 提供了 AgentExecutor 不具备的四个核心能力：1) 有状态图（StateGraph）让执行流可编程；2) Checkpointer 自动持久化状态，不需要手动管理 Redis 消息列表；3) RetryPolicy 在编译时声明节点级重试策略，比 try-except 更优雅；4) NodeInterrupt 支持人工审核介入。这些对生产级 Agent 都至关重要。但 LangGraph 的底层依赖仍是 LangChain 的消息体系和工具定义，所以两者不是替代关系而是配合关系。

### Q2：RAG 项目如何保证质量？

> 核心是建立质量评估闭环。我们集成了 RAGAS 框架，用 4 个指标（Hit Rate、MRR、Faithfulness、Answer Relevancy）量化评估检索和生成质量。每次知识库更新后自动运行评估，不达标则阻断上线。另外还设计了人机协同机制——文档分块后前端逐块预览确认，避免错误分块污染知识库。

### Q3：NL2SQL 怎么做安全防护？

> 三层防护：第一层只读事务，数据库连接层面禁止写操作；第二层表名白名单，LLM 生成的 SQL 只能访问预注册的业务表；第三层自动 LIMIT 200 防止结果过大。此外 SQL 执行错误会发给 LLM 自修复，最多重试 2 次。

### Q4：怎么控制 LLM 调用成本？

> 三点：1) 语义缓存，相似问题命中直接返回，节省约 15% 调用量；2) 模型降级，Qwen 限流时切换到更便宜的 DeepSeek；3) 分层分析，海量数据先用 SQL 聚合再送 LLM，避免 token 浪费在原始数据上。

### Q5：你这个项目有什么实际业务价值？

> 三个维度：降本（总部数据分析效率提升 70%，培训人力降低 60%）、提效（加盟商问题响应从 4 小时缩短到即时）、增收（及时差评回复预计为 500 家门店挽回年损失 200~300 万元）。每个指标都有明确的测量方法和 baseline。
