## 1. 项目概述

### 1.1 项目背景

本项目旨在为连锁中式快餐企业构建一套智能化的 AI 辅助管理系统，覆盖总部运营管理及加盟商日常经营的各个环节。通过引入大语言模型（LLM）、RAG（检索增强生成）、向量数据库、知识图谱等技术，提升企业在数据分析、员工培训、客户服务、门店运营等方面的效率与智能化水平。

**当前痛点：** 连锁中式快餐品牌普遍面临"规模扩张与管理半径"的矛盾。500 家门店分散在全国 31 省，总部人力和管理资源有限，难以对每家门店实现精细化运营。加盟商经营水平参差不齐，缺乏数据驱动的决策工具，依赖经验和直觉经营。传统 IT 系统提供的大量报表需要人工解读，实际决策指导价值有限。具体表现为：
- 日常经营数据依赖人工汇总分析，总部无法实时掌握各门店真实经营状况
- 加盟商遇到制度、流程、菜品等问题需反复电话/微信咨询总部，总部答疑负担重
- 门店风评需店长逐一查看各平台评论，差评响应滞后
- 菜品宣传素材依赖外包制作，成本高、周期长
- 新店选址缺乏数据支撑，依赖个人经验判断

### 1.2 项目目标

- 为总部提供多维度营业数据分析与行业洞察能力
- 为加盟商提供门店级的智能运营工具（智能备菜、风评分析、聊天助手）
- 构建企业知识库，实现公司制度、菜品专业知识的高效检索与问答
- 通过 AI 能力降本增效，覆盖菜品素材生成、外卖运营、客户沟通等场景

### 1.3 适用范围

适用于连锁中式快餐企业的总部管理部门及所有加盟门店。

### 1.4 业务价值

本系统围绕"降本、提效、增收"三大目标，为企业和加盟商带来可量化的业务价值：

| 维度 | 预期业务价值 | 关键支撑模块 |
|------|-------------|-------------|
| **降本** | 总部数据分析效率提升约 70%（AI 自动生成报告代替人工编写）；菜品素材外包成本降低约 60%（AI 生成替代外包设计）；培训人力投入降低约 60%（知识库自助问答代替讲师答疑）；食材损耗率降低 10%~15%（智能备菜优化） | 营业分析、素材生成、培训、备菜 |
| **提效** | 加盟商问题响应从平均 4 小时缩短至即时；差评发现与响应从 6~12 小时缩短至 1 小时以内；新加盟商上手周期从 2 周缩短至 3~5 天；新店选址评估效率提升 80% | 聊天助手、风评、培训、选址 |
| **增收** | 及时差评回复预计为 500 家门店挽回年损失约 200~300 万元；AI 选址辅助降低新店失败率；外卖运营优化提升线上订单转化 | 风评、选址、外卖运营 |

## 2. 用户角色与权限体系

权限体系采用 **RBAC（基于角色的访问控制）** 模型，支持角色的动态扩展。系统预置三个基础角色，后续可根据业务需求新增自定义角色并分配权限。

### 2.1 权限模型

```
用户 → 角色（可多角色） → 权限集合
```

- 角色与权限分离：一个角色可包含多个权限项，一个用户可拥有多个角色
- 权限粒度：功能模块级 + 数据级（如某门店范围）
- 动态扩展：通过管理后台新建角色、配置权限，无需修改代码

### 2.2 内部用户 — 老板

拥有系统最高权限，可访问所有功能模块的全局数据。

**核心职责：**
- 全局营业数据分析与决策
- 行业趋势研究与竞争分析
- 新门店选址评估
- 品牌风评全局监控
- AI 菜品图与视频素材生产
- 外卖运营策略制定与优化
- 加盟商管理
- 员工账号管理与权限分配

### 2.3 内部用户 — 普通员工

拥有部分运营模块的使用权限，受限于老板分配的数据范围。

**核心职责：**
- 协助营业数据整理与报表生成
- 行业信息收集与报告整理
- 培训资料维护
- 素材制作与处理
- 日常运营辅助工作

### 2.4 加盟商（Franchisee）

加盟商用户可访问**本门店维度**的数据与功能，获得日常经营所需的 AI 辅助能力。

**核心职责：**
- 本门店营业数据分析
- 本门店风评监控与复盘
- 智能备菜与采购管理
- 内部聊天助手（公司制度查询、菜品知识问答）
- 外卖运营辅助

## 4. 功能模块详细需求

### 4.1 营业数据分析

#### 4.1.1 概述

利用 AI 对门店经营数据进行多维度分析，自动生成分析报告，辅助经营决策。门店营业数据使用模拟数据，通过数据初始化脚本批量生成，存储在 MySQL。

**业务价值：** 传统 BI 系统只展示"发生了什么"，本系统让 AI 直接回答"为什么发生、该怎么办"。总部无需配备专职数据分析师即可获得结构化经营诊断，按 1 名数据分析师年薪 12 万计算，直接节省人力成本。同时 AI 对异常波动的即时发现（如某门店营收骤降 15%）比人工滞后发现提前 3~7 天，帮助总部及时干预、避免损失扩大。500 家门店的统一数据分析维度和标准，也解决了过去各区域报表口径不一的管理难题。

#### 4.1.2 数据说明

门店营业数据（订单明细、营业汇总等）均为**模拟生成数据**，不对接真实收银系统。通过脚本按以下规则生成：
- 设定门店基数，叠加随机波动生成每日营收
- 加入季节趋势、节假日效应等模拟真实业务形态
- 数据量级：每店每日数十至数百条订单记录
- 数据周期：每家门店从开业到 2026-05-17，开业时间在 2023-01-01 ~ 2025-07-02 之间随机（经营时长 10 个月 ~ 3 年 4 个月）
- 生成策略：按天循环，每天随机选取 85%~95% 的营业门店，每月提交一次数据库
- 支持按门店、日期范围重新生成或增量补充

#### 4.1.3 功能列表

| 功能 | 用户 | 描述 | 优先级 |
|------|------|------|--------|
| 门店维度分析 | 总部、加盟商 | 按门店查看营业数据，支持年度/月度筛选 | P0 |
| 总体维度分析 | 总部 | 查看所有门店汇总数据，支持年度/月度筛选 | P0 |
| 同比环比分析 | 总部、加盟商 | 支持与去年同期、上月的数据对比 | P1 |
| 趋势预测 | 总部 | 基于历史数据预测未来营收趋势 | P2 |
| AI 分析报告 | 总部、加盟商 | 基于数据自动生成自然语言分析报告，包含亮点、问题、建议 | P0 |
| 数据可视化 | 总部、加盟商 | 营收、客单价、翻台率等关键指标的图表展示 | P1 |

#### 4.1.4 数据维度

- 营收总额
- 订单数量
- 客单价
- 翻台率
- 各品类销量及占比
- 高峰时段分析
- 外卖 vs 堂食占比

#### 4.1.5 AI 分析报告要求

- 自动识别数据中的异常波动并给出原因分析
- 结合节假日等外部因素提供经营建议
- 报告格式支持结构化的"数据概览 → 关键发现 → 改进建议"

#### 4.1.6 大量数据的 LLM 分析方案

##### 核心问题

订单数据量达千万级（9M+ 订单、22M+ 明细），远超 LLM 上下文窗口上限，无法将原始数据直接送入模型。需要分层处理流水线：

```
原始数据（MySQL） → SQL 预聚合 → 指标计算 → LLM 分析 → 报告输出
                              ↑                       ↑
                        daily_summary 表        prompt 模板 + 指标数据
```

##### 分层策略

**第一层：SQL 预聚合**

所有聚合在数据库层完成，LLM 不接触原始明细数据。利用 `daily_summary` 表（每店每日一条）作为分析基础：

```sql
-- 示例：门店月度聚合（182k → 6k 条）
SELECT store_id,
       DATE_FORMAT(summary_date, '%Y-%m') AS month,
       SUM(total_revenue) AS revenue,
       AVG(avg_price) AS avg_price,
       SUM(total_orders) AS orders
FROM daily_summary
WHERE store_id = ? AND summary_date BETWEEN ? AND ?
GROUP BY store_id, month;
```

经过预聚合，数据量级变化：

| 分析范围 | 原始数据 | 预聚合后 | 缩减倍数 |
|----------|----------|----------|----------|
| 单店全年 | 18k 订单 | 365 条汇总 | ~50x |
| 全部门店某月 | 750k 订单 | 500 条汇总 | ~1500x |
| 全部门店全年 | 9M 订单 | 182k 条汇总 | ~50x |

**第二层：指标计算**

在 Python 业务层完成同比环比计算后，只将数值指标传入 LLM Prompt：

```python
def build_analysis_prompt(store_id, year, month):
    # 1. SQL 查当月数据
    # 2. SQL 查上月/去年同期数据（同比环比）
    # 3. 计算变化率、异常值
    # 4. 只传入聚合后的关键数字
    prompt = f"""
    门店 {store_id} 在 {year} 年 {month} 月的经营数据：
    - 营业额: {revenue}元 (环比 {mom_pct}%, 同比 {yoy_pct}%)
    - 订单量: {orders}单
    - 客单价: {avg_price}元
    - 堂食占比: {dine_in_pct}%
    - 外卖占比: {takeout_pct}%
    - 高峰时段收入占比: {peak_pct}%
    ...
    """
    return prompt
```

传入 LLM 的 token 数控制在 **500 tokens 以内**，远低于模型上下文上限。

**第三层：LLM 分析生成**

LLM 基于传入的结构化指标数据，生成自然语言分析报告：

- 异常波动解读（如"本月营收下降 15%，主要受暴雨天气影响（15 天降雨）"）
- 亮点提取（如"酸辣土豆丝销量增长 30%，建议加大备货"）
- 改进建议（如"外卖占比仅 18%，低于同商圈均值 25%，建议优化外卖运营"）

**第四层：分层下钻（可选）**

如果 AI 报告检测到异常，支持按需下钻查询明细：

```
月度异常 → 日维度明细查询 → 具体订单查询
  （AI触发）    （SQL查询）     （仅当需要）
```

避免每次分析都加载全量数据。

##### 技术实现要点

- 复用 `Base.Repository` 的 MySQL 查询能力，不走 Milvus 向量检索
- 用 `Base.RicUtils` 的日期工具类处理同比/环比周期计算
- 调用 `Base.Ai.llms.qwenLlm` 进行分析，使用专用分析 Prompt 模板
- 预聚合结果可缓存至 `Redis` 避免重复计算，TTL 设为 1 小时
- `daily_summary` 表的 `uk_store_date` 索引已覆盖门店+日期查询场景

##### 与传统 BI 对比

| 环节 | 传统 BI | AI 方案（本系统） |
|------|---------|------------------|
| 数据获取 | 相同（SQL 查询） | 相同 |
| 异常发现 | 人工看图表 | LLM 自动标注 |
| 原因分析 | 人工经验判断 | LLM 结合节假日等因素推理 |
| 报告生成 | 人工编写 | LLM 自动生成结构化报告 |
| 下钻分析 | 手动操作 | AI 建议 + 按需执行 |

### 4.2 行业分析

#### 4.2.1 概述

总部通过联网搜索获取国内外餐饮行业最新数据与趋势，自动生成行业分析报告。

#### 4.2.2 功能列表

| 功能 | 用户 | 描述 | 优先级 |
|------|------|------|--------|
| 联网搜索 | 总部 | 自动搜索国内外餐饮行业最新资讯、数据报告 | P0 |
| 竞品动态监控 | 总部 | 跟踪主要竞争对手的新品、活动、扩张动态 | P1 |
| 行业报告生成 | 总部 | 基于搜索结果自动生成结构化的行业分析报告 | P0 |
| 趋势预警 | 总部 | 识别行业重大变化（政策、原材料价格等）并推送预警 | P2 |

#### 4.2.3 技术实现要点

- 使用通义千问（Qwen）**内置的联网搜索能力**，通过 `enable_search=True` 参数开启，无需自建搜索模块
- 详细实现方式：在调用千问 LLM 时传入 `enable_search=True` 参数，模型自动联网获取最新信息后生成回答
- 支持定期自动生成报告（日报/周报/月报）

### 4.4 加盟商培训

#### 4.4.1 概述

面向新加盟商提供系统化的 AI 辅助培训，帮助快速掌握公司制度、菜品知识、运营规范等内容。

**业务价值：** 传统加盟商培训依赖总部讲师线下授课、人工答疑，一家 500 店规模的连锁品牌需配备 3~5 名培训专员，培训成本高、覆盖面有限。本系统将培训资料沉淀为可检索的知识库，加盟商可 7×24 小时 AI 自助问答，无需等待总部响应。总部培训人力投入降低约 60%，新加盟商上手周期从平均 2 周缩短至 3~5 天，显著加速新店爬坡期。同时 AI 在线考核功能确保每位加盟商在开业前完成关键知识点的学习验收，从源头降低经营风险。

#### 4.4.2 功能列表

| 功能 | 用户 | 描述 | 优先级 |
|------|------|------|--------|
| 知识库问答 | 总部、加盟商 | 基于 RAG 的公司制度、政策、流程问答 | P0 |
| 菜品知识学习 | 加盟商 | 学习公司菜品配方、制作工艺、标准化流程 | P0 |
| 培训课程管理 | 总部 | 上传、管理培训材料（文档、视频、PPT） | P1 |
| 学习进度追踪 | 总部、加盟商 | 记录学习进度，标记已完成/未完成内容 | P1 |
| 在线考核 | 总部、加盟商 | AI 出题并自动批改，检验学习效果 | P2 |

#### 4.4.3 知识库建设

- 知识分类：公司制度、政策法规、菜品知识、运营流程、SOP 标准
- **文档格式支持**：
  - **PDF**：支持文字型 PDF 的文本提取与向量化
  - **Word（.doc/.docx）**：支持文档段落解析与格式保留
  - 其他格式（PPT、Excel、图片、视频）作为辅助补充
- 文档解析流程：原始文件 → 文本提取 → 文本分块（chunking）→ Embedding 向量化 → 存入 Milvus
- **前端上传界面**：Vue 3 前端提供文档上传页面，支持拖拽或选择文件上传，上传后自动触发后端解析与向量化流程
- 更新机制：知识库内容更新后自动重新向量化

#### 4.4.4 RAG 实现要求

- 使用 Milvus 向量数据库存储文档 Embedding
- 结合 Qwen 的 Embedding 模型进行向量化（768 维）
- 检索策略：混合检索（向量相似度 + 关键词匹配）
- 支持多轮对话中的上下文引用溯源

### 4.5 风评分析

#### 4.5.1 概述

基于数据库中预置的模拟评论数据，利用 AI 分析各门店口碑表现，提炼洞察、生成回复建议。评论数据不对外部平台进行真实采集，通过模拟数据集模拟各平台（美团、饿了么、大众点评等）的用户评论。

**业务价值：** 差评发现从"店长自行查看"变为"AI 自动预警+回复建议"，差评响应时间从平均 6~12 小时缩短至 1 小时以内。及时、专业的差评回复可有效降低用户流失，提升店铺评分 0.2~0.5 星，直接影响外卖平台曝光权重和转化率。按 500 家门店估算，每家门店月均挽回 2~3 单差评导致的客户流失，预估年增收约 200~300 万元。同时 AI 聚合分析全网评论热点，帮助总部从"被动处理投诉"转向"主动优化产品与服务"，形成品牌口碑的正向循环。

#### 4.5.2 数据说明

评论数据使用**模拟数据**，存储在 MySQL，通过初始化脚本批量生成：

- 评论内容由 AI（LLM）根据预设模板和菜品信息批量生成，覆盖正面、负面、中性评论
- 数据量级：每店数百至上千条评论，支持按需扩充

| 公司制度问答（RAG） | 总部、加盟商 | 基于企业知识库检索的公司制度问答 | P0 |

|----------|:----:|:--------:|:------:|

| 联网搜索 | ✓ | ✓ | ✗ |

#### 4.7.4 技术实现

聊天助手采用 **LangChain Agent** 架构，以 `create_agent()` API 构建，按角色缓存为全局单例，通过 `contextvars` 实现会话隔离。

##### Agent 架构

```
用户输入 → POST /api/v1/chat/ask
  → chatService.ask_stream()
      → AgentMemory.get_or_create_session()  # 会话管理
      → get_agent_for_role()                 # 获取/创建角色 Agent 全局单例
      → AgentMemory.build_memory_messages()  # 加载记忆上下文
      → agent.astream()                      # LangGraph Agent 流式执行
          ├─ ChatMemoryMiddleware            # 超阈值自动摘要压缩
          ├─ LLM (通义千问 via ChatOpenAI)    # 模型推理
          └─ @tool 工具调用                   # 按需选择执行
      → 逐 token yield SSE 事件
      → push_to_redis() + save_conversation() # 记忆持久化
```

##### Agent 工具集

| 工具名 | 触发场景 | 实现方式 |
|--------|---------|----------|
| `knowledge_search` | 公司制度、菜品知识、SOP 流程等知识类问题 | 通义千问 LLM 基于知识库回答 |
| `data_query` | 营业额、订单量、客单价、菜品排行等数据类问题 | LLM 理解查询意图，分析数据结构后给出结果 |
| `web_search` | 行业新闻、竞品动态、最新政策等需要实时信息的问题 | 通义千问内置联网搜索（`enable_search=True`） |
| `general_chat` | 闲聊、问候、情感交流等无工具匹配时的兜底回复 | 直接调用通义千问对话 |

##### 对话记忆管理

采用 **双层记忆存储 + 自动摘要压缩** 的分层策略：

| 层级 | 存储 | 用途 | TTL |
|------|------|------|-----|
| 短期记忆 | Redis（`agent:memory:{session_id}`） | 最近对话消息列表 | 24h |
| 摘要 | Redis（`agent:summary:{session_id}`） | AI 压缩的会话摘要 | 7d |
| 持久化 | MySQL（`base_llm_conversation`） | 全量对话记录 | 永久 |
| 会话元数据 | MySQL（`base_llm_session`） | 会话信息与摘要 | 永久 |
| 向量 | Milvus | 向量检索 | 永久 |

**记忆加载优先级：** Redis 消息列表 + Redis 摘要 → 两者任一不存在则从 MySQL 回退加载并同步到 Redis。组合为 `[摘要SystemMessage] + [历史对话HumanMessage/AIMessage]` 注入 Agent。

**记忆压缩策略（ChatMemoryMiddleware）：** 当消息超过 15 轮或 5000 字符时，自动对早期对话使用 LLM 生成智能摘要，保留最近 5 轮完整消息。摘要同步更新到 Redis 和 MySQL。

##### 流式响应方案

- 后端：FastAPI `StreamingResponse(content_type="text/event-stream")`，Agent 的 `astream()` 逐 token 产出
- SSE 事件格式：`data: {"type":"start"|"content"|"done"|"error", "content":"...", "session_id":"..."}\n\n`
- 前端：原生 `fetch` + `ReadableStream.getReader()` 读取流，支持 `AbortController` 取消请求
- 非流式兜底：同步调用 `agent.arun()` 一次返回完整结果

##### API 接口

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/v1/chat/ask` | POST | 统一对话入口，支持流式/非流式 |
| `/api/v1/chat/session/list` | GET | 获取用户会话列表 |
| `/api/v1/chat/session/create` | POST | 创建新会话 |
| `/api/v1/chat/session/delete` | DELETE | 删除会话 |
| `/api/v1/chat/session/history` | GET | 获取会话对话历史 |

##### 权限隔离

- **老板/普通员工**：注册全部 4 个工具
- **加盟商**：仅注册 `knowledge_search` + `data_query` + `general_chat`（无 `web_search`）
- 权限在 Agent 构建时通过 `_get_tools_for_role()` 过滤，按角色编码缓存不同 Agent 实例

##### 全局单例与上下文隔离

- 按角色组合缓存 Agent（`_role_agents: dict`），避免每次请求重复构建
- 通过 `contextvars.ContextVar`（`_session_id_var` / `_user_id_var`）在中间件中动态获取当前会话上下文，实现单例 Agent 的多会话隔离

### 4.11 系统管理

#### 4.11.1 概述

系统管理模块为总部管理员提供系统级配置管理能力，采用 **RBAC（基于角色的访问控制）** 权限模型，支持用户、角色、菜单的统一管理，以及定时任务的动态配置。所有系统管理功能仅对 **老板** 角色开放。

该模块包含五个子功能：用户管理、角色管理、菜单管理、角色授权（菜单关联）、定时任务管理。

#### 4.11.2 权限模型

系统管理模块采用标准的 RBAC 权限模型：

```
用户 → 多角色绑定 → 角色 → 多菜单绑定 → 菜单/权限集合
```

- **用户**：系统登录账号，一个用户可绑定多个角色
- **角色**：权限集合的载体，一个角色可关联多个菜单/权限
- **菜单**：功能菜单与权限标识的统称，以树形结构组织，包含三种类型：
  - 目录：最顶层菜单分组
  - 菜单：可点击的功能页面
  - 按钮：页面内的操作权限（如新增、编辑、删除等）
- 权限粒度：支持到按钮级别（通过 `permission_code` 权限标识控制）

#### 4.11.3 数据模型

系统管理相关表存储在 `ric_ai_base` 数据库中（Base 模块数据库），与业务数据分离。

| 表名 | 说明 | 备注 |
|------|------|------|
| `sys_user` | 系统用户表 | 存储登录账号信息，密码使用 bcrypt 哈希加密 |
| `sys_role` | 角色表 | 角色名称、编码、状态等 |
| `sys_menu` | 菜单权限表 | 树形结构（parent_id 自关联），含目录/菜单/按钮三种类型 |
| `sys_role_menu` | 角色菜单关联表 | 多对多关系，一个角色可关联多个菜单 |
| `sys_user_role` | 用户角色关联表 | 多对多关系，一个用户可拥有多个角色 |

##### 4.11.4.4 角色授权（菜单关联）

| 功能 | 用户 | 描述 | 优先级 |
|------|------|------|--------|
| 获取角色菜单 | 老板 | 获取指定角色已分配的菜单/权限 ID 列表 | P0 |
| 分配菜单权限 | 老板 | 为角色分配菜单/权限（以树形菜单勾选方式） | P0 |

**交互说明：**

- 前端以树形菜单展示所有菜单/权限，已勾选的表示该角色已有权限
- 勾选父节点时，自动勾选所有子节点
- 取消勾选子节点时，父节点状态自动变为半选
- 保存时仅提交勾选的菜单 ID 列表
- 后端采用全量替换策略（先删除角色所有旧关联，再批量插入新关联）

**业务规则：**

- 一个角色可以关联多个菜单/权限
- 按钮类型权限必须挂在某个菜单类型的节点下
- 角色权限变更后，已登录用户需要重新登录才能生效

#### 4.11.6 技术实现要点

- **数据库**：系统管理表统一存储在 `ric_ai_base` 数据库（Base 模块数据库），与业务数据库 `catering_ai_system` 分离
- **ORM 模型**：所有模型继承 `BaseModuleDBModel`，利用 Base 框架的自动 CRUD 能力
- **密码加密**：使用 `passlib` 库的 bcrypt 算法进行密码哈希存储，不保存明文密码
- **定时任务**：基于已有 APScheduler 能力，通过 `TaskSchedulerClient` 管理任务的创建、暂停、恢复和删除
- **菜单树**：采用 parent_id 自关联方式构建树形结构，后端返回扁平列表 + 前端构建树，或后端直接返回树形 JSON
- **权限标识**：采用 `sys:模块:操作` 的命名规范，如 `sys:user:add`
- **角色授权**：使用全量替换策略（删除旧关联 → 批量插入新关联），在一个事务中完成

### 8.2 数据生成脚本

模拟数据生成脚本位于 `doc/sql/` 目录：
- `schema.sql` — 12 张业务表的完整 DDL（门店、菜品、会员、堂食订单、外卖订单、订单明细、营业汇总、评论、用户等），其中库存、采购相关表因智能备菜模块暂不实现，已注释
- `generate_data.py` — 数据生成与批量插入脚本，支持自定义门店数量、日期范围、数据库配置
- `README.md` — 使用说明

> **注意**：系统管理模块（`sys_user`、`sys_role`、`sys_menu`、`sys_role_menu`、`sys_user_role`）的表结构 DDL 定义在代码模型层中（`CateringAiSystem/Models/`），通过 Base 框架的 `create_table_sql` 自动建表，无需手动执行 SQL。这些表存储在 `ric_ai_base` 数据库（Base 模块数据库）中，与业务数据库分离。

生成的数据特征：
- **门店**: 500 家，均匀分布全国 31 个省级行政区，命名格式 `省份+城市+xxx店`
- **订单**: 每店每日数十笔订单，每条记录区分微信支付/支付宝支付/现金支付，每条订单含 1~4 道菜品
- **数据周期**: 每家门店从开业到 2026-05-17，开业时间在 2023-01-01 ~ 2025-07-02 之间随机（经营时长 10 个月 ~ 3 年 4 个月），含节假日倍率、季节效应
- **营业额**: 每店每日 1000~3000 元，客单价 22~38 元
- **菜品**: 56 道中式快餐，按 popularity 权重随机选菜
- **会员**: 暂不生成（会员画像模块未实现，member_id 均为 NULL）
- **生成策略**: 按天循环生成，所有营业门店均生成数据（处理顺序随机），订单时间集中在午餐（11:00-13:00）和晚餐（17:00-19:00），每月提交一次数据库
